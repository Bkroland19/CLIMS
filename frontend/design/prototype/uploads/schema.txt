Overview & methodology
The legacy CLIMS database (MySQL, ported column-for-column to Postgres) has no real foreign keys: almost
every relationship is an untyped varchar column holding a district UID, a hotspot id, or the literal string ‘jms’,
matched by the application at query time rather than by the database. Several columns are also overloaded —
the same field holds a user id in one row and a hotspot id in another — and a number of columns are legacy
artefacts that are always NULL or always blank.
This target schema normalizes that structure: every relationship becomes a typed uuid foreign key, every
overloaded column is split into the distinct relationships it was standing in for (for example, a transaction's
polymorphic ‘receiving organization unit’ becomes two columns, receiving_store_id and receiving_hot_spot_id),
and legacy columns that were never populated are left out. New tables were added where the legacy design
was missing a concept entirely — role-based permissions, an audit trail, a proper contact-person entity, and
sessions — and every table now carries created_at/updated_at and a uuid primary key.
The design went through five drafts: an initial normalization pass, a request to use uuid keys and round out the
users/roles/organisation_units/condom_inventories tables, a round adding audit, session, contact-person and
hot-spot fields, and a final pass reconciling every table against the legacy source file the project team supplied
(3_erd_target_postgres.html) — which caught a handful of genuinely missing fields and corrected two earlier
guesses (see the sections below).
Design decisions
Users’ working area — Resolved. users.store_id and users.hot_spot_id (whichever is set) now determine a
user's area. The earlier region_id/district_id/subcounty_id columns on users were redundant with that and have
been removed.
Stock-holding locations — Resolved. The legacy data only ever uses ‘jms’ or a district UID as a stock-holding
location, never a facility-level organisation unit. That confirms stores (not organisation_units) is the right target
for condom_inventories.store_id, transactions.sending_store_id/receiving_store_id, and orders.
One hot spot per user — Resolved. A user can cover more than one hot spot. hot_spot_user is a new join
table for this — the legacy schema even had an empty, unused hotspot_user_mappings table for the same
purpose. users.hot_spot_id remains as the user's primary/default hot spot.
Orders and the condom being ordered — Resolved. orders.condom_id now names the product an order is
for. The legacy orders table had no such column at all, which was flagged as an open question from the first
draft.
condom_inventories.organisation_unit_stocking — Resolved. An earlier draft added this as a separate
facility-level column alongside store_id. The source file shows it is the same underlying value as store_id (both
are ‘district UID or jms’), so the duplicate column was removed and store_id kept.
hot_spots.type / hot_spots.status — Corrected. An earlier draft put a ‘permanent or not’ type and an ‘active
or inactive’ status on contact_persons. The source file confirms both columns actually belong on hot_spots, so
they were moved.
Role → permission model — New. The legacy schema stored a single role per user as free text (roles.id as a
string). The target schema adds roles, permissions, role_permission and role_user so a user can hold more
than one role and a role can hold more than one permission.
Orphaned notifications (legacy data) — Open — not a schema question. Existing user_notifications.order_id
values in the legacy data point at an orders table that is empty. This is a data-migration concern for whoever

Still open for confirmation
The legacy source file doesn't cover every table in the target schema (it has no stores or contact_persons table
at all), so a few fields are still best-guess additions rather than confirmed by source. They're marked ‘inferred —
confirm’ on the diagram and listed here:
l contact_persons.name and contact_persons.phone_number — a contact person needs to be identifiable
somehow; no source table exists to confirm the field names.
l stores.name — the legacy data has no stores table at all (stock locations are bare text codes), so this is a
new, unconfirmed field.
l users.location — present in the source (varchar(15)) but its meaning isn't documented; kept as-is pending
clarification.
